Operations

This page covers the commands and operational behavior that matter most for local development and production deployment.

Build And Run​

Common commands:

make build
make run CONFIG=path/to/config.hcl
make validate CONFIG=path/to/config.hcl

Direct CLI usage:

aiproxy serve
aiproxy validate
aiproxy login github-copilot --client-id YOUR_GITHUB_OAUTH_CLIENT_ID --credential copilot-main
aiproxy paths
aiproxy examples
aiproxy configure
aiproxy configure provider
aiproxy serve --config /etc/aiproxy/config.hcl
aiproxy validate --config /etc/aiproxy/config.hcl
aiproxy version

Without --config, the CLI reads $XDG_CONFIG_HOME/aiproxy/config.hcl, falling back to ~/.config/aiproxy/config.hcl when XDG_CONFIG_HOME is unset. Set $AIPROXY_CONFIG to inline HCL to skip the config file (explicit --config overrides it; serve -d and configure/login file workflows require a file).

Foreground aiproxy serve is supported across the advertised release targets. Linux additionally supports aiproxy serve -d and the aiproxy status, aiproxy stop, and aiproxy restart daemon lifecycle commands. On non-Linux platforms those daemon lifecycle commands return daemon lifecycle is unsupported on this platform.

When running locally with env-based secrets, load your environment before invoking the binary:

set -a; . ./.env; set +a

Helm NetworkPolicy​

The helm/main chart enables release-scoped default-deny policies. Empty API or relay ingress source lists deny ingress; add explicit caller/router peers, allowSameNamespace (same-release pods), or allowOpenShiftIngress as appropriate. Upgrade note: empty source lists previously rendered an unrestricted ingress rule. Configure the intended sources before upgrading instead of relying on that behavior.

For a relay fronting this release's API, explicitly enable the narrow upstream connection on both policy surfaces:

relay:
  enabled: true
  env:
    UPSTREAM: http://aiproxy-api:8080
networkPolicy:
  relay:
    allowApiUpstream: true
    ingressFrom:
      - podSelector:
          matchLabels:
            app.kubernetes.io/name: trusted-caller

Replace aiproxy with the release name and adjust service overrides/caller labels as needed. allowApiUpstream defaults to false, requires both components to be enabled, and allows only relay egress plus API ingress between same-release pods on the configured API service port. It never opens relay ingress. External upstreams require explicit CIDR or extraEgress rules instead. Run make helm-test with Helm installed to check the rendered policy contracts; these checks do not exercise a live cluster's NetworkPolicy implementation.

Configure Wizard​

aiproxy includes an interactive config editor for the top-level HCL blocks and the provider secrets JSON file.

Interactive entrypoints:

aiproxy configure
aiproxy configure provider
aiproxy configure auth
aiproxy configure alias
aiproxy configure listener
aiproxy configure upstream
aiproxy configure logging
aiproxy configure provider-health
aiproxy configure dashboard
aiproxy configure multi-tenancy

The root aiproxy configure command shows a block selector. The block-specific subcommands can also be used directly.

Supported workflows:

  • create or update listener, root upstream_header_timeout/encrypted_reasoning, auth, provider, alias, logging, and provider_health
  • update provider secrets when using api_key_ref
  • configure the Dashboard API (dashboard) and embedded browser app (web_ui) independently
  • configure multi_tenancy and its database block together
  • delete existing blocks on commands that support --delete

For scripted environments, use --non-interactive on block subcommands.

Dashboard, Web UI, and Multi-tenancy​

In Dashboard & Web UI, enable the Dashboard API if you want the TUI or live browser dashboard. Enable the embedded Web UI separately if you want browser access. The Web UI alone supports workspace management if multi-tenancy is on; otherwise it only serves the app shell. No database is needed for the Dashboard API or Web UI themselves. The dashboard token defaults to server-generated; existing token settings are kept unless you change them or disable the Dashboard API, which removes the dashboard block.

In Multi-tenancy, reuse the existing PostgreSQL URL or supply the name of an environment variable for the wizard to write as database.url = env("..."). The wizard defaults public registration to off for new setups and preserves existing choices. An enabled, hand-written multi_tenancy {} still implicitly allows public registration unless the attribute is explicitly changed. Disabling multi-tenancy leaves the database block and stored data in place.

For an invite-only launch, explicitly close public registration, enable the Web UI, then create an invitation in the intended workspace. Direct the recipient to the clean /invite page on your deployment and send the one-time code separately over a trusted channel. The recipient pastes it into the form. Never put the code in a URL (path, query, or fragment). The app does not persist the entered code; delivery services, clipboard history, extensions, or password managers may retain copies outside the app's control.

Treat old code-bearing links as exposed. Revoke affected pending invitations as a system administrator from Users → Pending invites, or with authorized DELETE /_internal/admin/invites/{id}, then issue new codes and deliver them separately. Opening the current page cannot undo an earlier visit: fragments can persist in browser history, and path/query values may also be in access or proxy logs.

Acceptance creates the account and intended membership atomically. The recipient then signs in with their invited email/password, or with SSO using that same existing account. SSO never creates unknown accounts, even with public registration open; pending invitations must be redeemed first. Returning users keep their memberships, without automatic System enrollment. IdP/mock verification is not evidence of compatibility with a particular live identity provider.

aiproxy configure dashboard --config ./config.hcl --non-interactive --dashboard --web-ui
aiproxy configure multi-tenancy --config ./config.hcl --non-interactive \
  --enabled --database-url-env AIPROXY_DB_URL --allow-public-registration=false

Use --dashboard=false, --web-ui=false, or --enabled=false to turn the respective feature off. Use --token-env NAME to set a dashboard token reference or --token-env= to remove the explicit token and use the server's automatic token handling.

Enabling the Dashboard API, toggling multi-tenancy, or changing the database URL while multi-tenancy is enabled requires a restart. Web UI and public registration changes can apply on SIGHUP. The wizard only edits the file. For first-time multi-tenancy setup, provide the database URL to the migration and serving processes, set AIPROXY_JWT_SECRET for the server, and set AIPROXY_ADMIN_EMAIL and AIPROXY_ADMIN_PASSWORD before running aiproxy migrate up --config ./config.hcl to seed the first administrator on a fresh database.

Set auth.mode = "bearer_static" to serve inference in a multi-tenant deployment. none still permits management but disables authenticated data-plane access; a browser session cannot substitute for an inference bearer. When upgrading from a catalog shared in practice, use HCL clients for System and issue database keys in the same workspace as their intended models. A new workspace starts empty. Repair alias targets and provider inheritance references that span workspaces before upgrading: the merged catalog now rejects them at startup/reload, including disabled derivatives. Public names do not change.

Workspace Isolation Upgrade And Recovery​

Compatibility change: System inventory is not shared with tenants. Inheritance bases and all alias targets (including shorthand) must be in the resource's destination workspace, even for global-administrator-authored rows. Disabling a derivative does not make a foreign base valid. A newly added HCL provider or alias cannot shadow a managed name, regardless of the provider's enabled state. Names remain globally unique; there is no automatic rename, ownership transfer, sharing mode or per-tenant copy of HCL inventory.

Before replacing a running binary:

  1. Back up the config and database. Use the candidate binary with the same config, database URL, secret environment and database encryption key as serve. Apply any pending migrations using the normal migration procedure.

  2. Run the operator preflight:

    aiproxy validate --config /etc/aiproxy/config.hcl --check-db

    This reads and validates the merged catalog without starting a server or sending inference. It may resolve configured local credential references. Check the exit status and database catalog: valid result: the earlier config is valid line only validates the file. Plain validate does not check managed rows. Preflight reports the first error; repeat after repairs.

  3. Audit db_providers.extends and db_alias_targets.provider/model against the referenced provider's workspace_id; file-defined names belong to System (00000000-0000-0000-0000-000000000000). Check HCL names against all managed provider/alias names, including disabled providers.

  4. Retarget or remove invalid aliases and derivatives. To keep a tenant model, configure an independently owned provider/base in that tenant with its own credential and a globally unused name; do not copy System credentials. Changing a derivative to concrete requires valid local model definitions, and policy-bearing inheritance transitions require an explicit models replacement. Update callers and allowlists if public names change.

  5. Repeat preflight until it passes, then restart. Verify each workspace's model list and own direct/alias calls with its inference key.

If a running instance rejects a reload, its previous runtime remains active; do not restart into a known-invalid saved graph. Use authorized management updates with known resource names to replace bad references, or remove those referrers. Legacy invalid views may return a controlled error rather than foreign inventory, so use the operator's trusted database audit to locate them.

Provider and alias updates/deletes, provider credential updates, named Copilot device-flow starts, and existing-key policy updates, deletes, rotations and revocations now return the same resource-specific 404 for missing targets, hidden targets, and valid workspace selectors that do not match. A 404 alone does not prove absence. Before retrying, verify your account and selected workspace against authorized inventory. Check every query and header selector and any supported body selector, even as a global administrator. Omit unused selectors; empty or malformed IDs return 400. These denials save nothing and do not trigger a reload or contact the Copilot issuer. See direct catalog writes and direct key writes.

If startup is already blocked, repair the config or perform narrowly scoped, transactional database maintenance while serving is stopped. Preserve resource and workspace IDs, credentials and key ownership; follow the catalog updated_at revision protocol for direct SQL edits. Prefer removing the new HCL collision over silently renaming an existing managed resource. A deliberate rename requires updating all affected same-workspace aliases, derivatives, allowlists and callers. Preflight again before starting.

The portal validates the saved workspace choice before querying inventory. Global administrators default to System even when a tenant sorts first; tenant users prefer an authorized non-System workspace. Explicit System members remain read-only there, and an account with no memberships has no tenant write target. Reference pickers and empty-state creation use only the selected workspace. Changing workspace/account discards old views and prevents pending forms, credential recovery queries or mutations from reusing the new context.

Managed catalog writes serialize dependency changes in the database; see safe catalog cleanup. An already-admitted server mutation cannot be undone by browser cancellation. Saves request immediate local activation; other replicas reconcile durable revisions independently, without a cluster-wide acknowledgement. See bounded replica convergence.

Tenant Provider Policy Upgrade​

Intentional compatibility change: non-System managed providers/probes no longer have unrestricted outbound destinations, host secret references, caller-token forwarding or cleartext exceptions. Even a global administrator editing a tenant row must follow the tenant policy. System and file-only workflows are unchanged; no new database schema migration is needed for the operator's allowed_upstream_origins attribute.

Before upgrading:

  1. Back up config and DB, apply pending migrations, and audit all non-System db_providers rows, including disabled rows. Check nonempty api_key_ref_path/api_key_ref_key, copilot_credential_path/ copilot_credential_name, forward_authorization, allow_insecure_base_url, effective/inherited base_url and health targets.

  2. Approve only needed exact public HTTPS origins in multi_tenancy.allowed_upstream_origins. Include provider-type defaults and absolute health origins/ports where used. Do not approve a private service, wildcard or metadata endpoint; there is no production private/mock bypass. Approval grants network permission, not resource or credential ownership.

  3. Replace tenant file references with credentials owned by that tenant: encrypted API key writes or its own Copilot database device flow. Do not copy System secrets. Clear both path and key/name members of legacy references, remove caller forwarding and cleartext flags, and retarget upstreams/probes to approved HTTPS destinations. Disabling a provider is not a policy repair. Repair a derivative's effective settings on its own same-workspace base; removing an existing healthcheck is unsupported, so retarget it.

  4. Run with the candidate binary, serving config/secret environment and database encryption key:

    aiproxy validate --config /etc/aiproxy/config.hcl --check-db

    Check the exit status and database catalog: valid, not only the earlier config is valid line. Plain validate checks only the file. DB preflight materializes and checks all destination policies before DB credential decryption or file resolution; forbidden tenant configurations never read host credentials. Trusted HCL references may still resolve while loading the file, and a valid System DB reference may resolve after preflight. This is read-only catalog validation, not DNS/network or live-provider verification. Repeat after each reported repair.

  5. Restart only once preflight passes; verify each tenant's own JSON/SSE inference and configured probes. DNS answers are checked on every new connection, with verified TLS and no environment proxy, so approved names that resolve privately or have invalid certificates remain unusable.

Authorized updates can repair known old rows while an instance still serves. For a sidecar-to-Copilot-DB switch, first clear the legacy reference and repair destinations (temporarily disabling the provider if it has no DB credential). Then start an own device flow and consume it in provider PUT. Provider-bound device start/poll also reject forbidden effective tenant configurations before issuer I/O; standalone authorization retains its fixed trusted issuer workflow and does not itself activate any upstream. If startup is blocked, use the narrowly scoped transactional maintenance and revision precautions above. Never automatically transfer a tenant provider into System or convert a host secret into a tenant secret.

Approvals reload with the file. Removing an approval while a stored provider or probe still requires it rejects the candidate; the previous runtime, including its previous approvals and already-admitted work, remains active. Retarget/remove dependent rows and repeat preflight, then reload; do not treat a failed reload as approval revocation. Activation is still local to the receiving instance, not cluster acknowledgement; DB changes reconcile as described under bounded replica convergence. File policy changes still require deployment to every replica.

GitHub Copilot is hermetically verified; live GitHub compatibility unverified. See mock-only verification for local checks requiring no real client ID/account. Production login below contacts GitHub; configure provider only references its saved credential (no API-key flags, OAuth networking or token display in configure). The model name is illustrative:

aiproxy login github-copilot --client-id YOUR_GITHUB_OAUTH_CLIENT_ID --credential copilot-main

aiproxy configure provider \
  --config /etc/aiproxy/config.hcl \
  --non-interactive \
  --name copilot \
  --type github-copilot \
  --credential copilot-main \
  --model gpt-5.4-nano

login prints the verification URI and user code, then writes <secrets-dir>/copilot-<name>.json (0600). It never edits HCL or signals a server: restart or SIGHUP to activate, and re-run the same login + reload on upstream 401/403, revocation, or expiry. Use your own public OAuth client ID; never reuse another application's client ID.

The web provider form offers the same authorization as Connect GitHub: enter the public OAuth client ID, approve at the shown URL with the shown code, then save the provider to apply. The browser never receives tokens; the server stores the credential encrypted in the database. CLI sidecar and Connect GitHub are alternatives; Copilot Rotate in the web UI opens reauthorization.

Connect GitHub details: the server performs the device challenge over the fixed GitHub issuer, fixed read:user scope, and the fixed verification page, then stores the result as an AES-GCM-encrypted database credential (never a sidecar, never a raw-token API input). The same database encryption key must be configured on every instance or the saved credential fails to decrypt. Unfinished device sessions expire (pending is bounded by the issuer expiry and 15 minutes, ready lasts 10 minutes) and are reaped by a bounded per-minute cleanup (100 rows per batch); provider saves set X-Aiproxy-Catalog-Saved: true once the database commit is durable, including saved-but-activation-failed outcomes where the old runtime stays active. Activation applies to the receiving instance only; there is no cluster broadcast; durable DB revision polling activates other replicas (or their next mutation picks the catalog up). Hermetically verified; live GitHub compatibility unverified (see below).

Inference preserves upstream JSON 401/403 errors without implicit re-login; models --upstream adds a re-login hint. A new listing invocation reads the new sidecar immediately after login, while the running server still requires reload.

Editing Encrypted Reasoning Policies​

The existing configure upstream command edits root policy; configure provider edits provider policy and selected models; configure alias edits alias policy. Interactive choices distinguish preserve, inherit/remove, reset, override. There is no separate root/model command. For all three commands:

FlagEdit
--encrypted-reasoning-passthrough[=true|false]Set the member; use =false to pre-strip.
--encrypted-reasoning-on-caller-mismatch fail|strip_and_retrySet the member; --encrypted-reasoning-on-caller-mismatch= writes explicit "" (fail).
--encrypted-reasoning-match-message TEXTRepeat to replace the list; a single --encrypted-reasoning-match-message= writes [] (built-ins).
--no-encrypted-reasoningRemove the local block and inherit.
--reset-encrypted-reasoningWrite a present empty block (safe reset), not inheritance.

Provider model controls use existing model names (including slash-separated names):

FlagValue
--model-reasoning-passthroughname=true or name=false
--model-reasoning-on-caller-mismatchname=fail, name=strip_and_retry, or name=
--model-reasoning-match-messagename=TEXT; repeat per model to replace its list; a single name= selects []/built-ins
--no-model-reasoningModel name; remove the local policy
--reset-model-reasoningModel name; declare local empty reset

Repeat model flags for different models and quote values containing spaces. Duplicate scalar/control edits for one model reject. Remove/reset/member edits conflict within the same scope/model; an empty pattern entry cannot be combined with other entries. Pattern normalization and 16-entry/4–256-byte bounds are checked before publication. The two scope-level boolean remove/reset flags set to =false are no-ops; model controls take names, not booleans.

With the complete scoped example saved as config.hcl and its environment variables set:

aiproxy configure upstream --config config.hcl --non-interactive \
  --encrypted-reasoning-on-caller-mismatch strip_and_retry
aiproxy configure provider --config config.hcl --non-interactive --name secondary \
  --model-reasoning-passthrough chat=false \
  --model-reasoning-match-message 'chat=caller binding mismatch'
aiproxy configure provider --config config.hcl --non-interactive --name secondary \
  --reset-model-reasoning chat
aiproxy configure alias --config config.hcl --non-interactive --name safe_pool \
  --no-encrypted-reasoning

Omitted edit flags preserve local intent exactly. Member edits preserve untouched members of an existing local block, unlike an admin API whole-object replacement. New blocks use built-ins for omitted members, never copy effective lower-layer values. Policy-only root edits need no timeout flag.

Editing stays HCL-only, preserves untouched env() spelling and supported comments, and validates before publishing; invalid edits do not change config or staged secrets. HCL/JSON conversion instead resolves env() at conversion time, while retaining absent/reset/false distinctions. Changes activate only after restart or successful SIGHUP.

Model controls alone never create definitions. On a derivative, they create only sparse existing-name reasoning overlays using a valid, loadable base inventory; they cannot repair a partial/invalid base, redefine models or relax credential/chain/deferred restrictions. Removing the last reasoning block removes a reasoning-only child model overlay, but retains a deferred sibling block. Inherited model policies still outrank child provider policies.

Configuring Provider TLS Profiles​

The wizard and scripted provider edits support the provider-only ClientHello settings. With an existing config/config.hcl and the measured recipe copied as described in the local capture workflow:

aiproxy configure provider \
  --config config/config.hcl \
  --non-interactive \
  --name measured-bun \
  --type openai-compatible \
  --base-url https://api.example.test/v1 \
  --api-key-env UPSTREAM_API_KEY \
  --tls-client-hello custom \
  --tls-client-hello-spec-file tls/bun-1.4.4-fetch.json \
  --model example-model

Omitting TLS flags preserves existing selections, custom references and env() spelling. Explicit --tls-client-hello native resets a concrete provider; choosing a non-custom profile removes an old custom reference when the file flag is omitted. Explicit empty flags or a file flag with a non-custom selector are rejected. Derived providers inherit both fields and cannot declare either flag. A scripted concrete-to-derived transition clears old local TLS settings when both are omitted. The interactive default choice removes the declaration; default is not a config selector. Editing/validation performs no provider networking and does not activate the running server until restart or SIGHUP. Conversion resolves custom paths to absolute host-local references; it does not copy profile files.

Local Bun ClientHello Capture​

The optional standalone developer tool requires the repository Go toolchain and an already installed Bun. It does not install tools or become a dependency of the serving binary. Initially only Bun fetch, fresh first-flight TLS and default experimental HTTP/2/HTTP/3 flags off are supported; there is no automatic Bun profile. Run from the repository root:

mkdir -p tls
go run ./scripts/tls-clienthello capture --bun bun --api fetch --samples 3 --out tls/bun-fetch.json --metadata tls/bun-fetch.metadata.json
go run ./scripts/tls-clienthello compare --bun bun --api fetch --samples 3 --spec tls/bun-fetch.json

Output directories must exist and recipe/metadata paths must be different. --samples accepts 2–16 (default 3). Capture publishes only after the recipe passes validation and all structural comparisons match. Existing regular outputs require explicit --force; symlink/special-file destinations are rejected even with it. Outputs use 0600. The two publications are not one filesystem-wide transaction; see tool usage and limits for failure/partial-publication semantics. compare prints a separate JSON report and exits nonzero on mismatch. It does not rewrite the supplied spec.

--bun bun resolves a recognized asdf shim safely to the direct installed binary without inheriting provider secrets; other wrappers fail with guidance. Selecting --bun "$(asdf which bun)" explicitly is also supported. The executable is trusted operator input, not sandboxed hostile code. Each fresh child uses a minimal explicit environment, isolated HOME/cwd, empty Bun config, no dotenv or auto-install, disabled proxies and a literal loopback URL with synthetic localhost SNI. The parent environment is unchanged. The listener stops after ClientHello: no provider credentials, external application traffic, HTTP body, certificate-verification bypass or privileged packet capture is needed. Capture/compare is not a complete TLS handshake. Accept/read is bounded to three seconds, child execution to five; sockets close and canceled children are reaped. Record/handshake and child-output bounds are documented with the tool.

The exporter emits the accepted native-shaped JSON, not json.Marshal(ClientHelloSpec). Metadata separately records runtime version/revision/platform/API, conditions, dependency/schema/policy pins, digests and comparison results, without machine paths, credentials or session secrets. Comparison checks actual byte structure, ordering, record framing/lengths, SNI, ALPN, GREASE and share groups/lengths, normalizing only random, session-ID bytes and real key-exchange bytes. JA3/JA4 alone is insufficient. Unsupported/resumption-dependent data and padding policies that cannot be inferred are rejected rather than approximated.

The committed Bun 1.4.4 fetch recipe and metadata are measured, not an illustrative Chrome preset: Linux x64, three fresh Bun and three uTLS samples, matching 1500-byte initial records, HTTP/1.1-only ALPN and MLKEM/X25519 shares, with no GREASE, ALPS, padding or residual structural differences. Separate local synthetic-trust tests verified materialized TLS 1.2/1.3 handshakes. This does not verify other Bun versions/APIs/options, SNI lengths, resumed TLS, the full HTTP/TCP stack, live providers or WAF/bot acceptance, and is not new TLS-specific binary integration evidence. Use version/API-specific output names for new captures.

Using A Recipe With Static Configuration​

Copy a recipe into the config directory, not merely the shell's working directory. For example, from the repository root with an existing config/config.hcl, create a new recipe destination:

mkdir -p config/tls
cp -- examples/tls/bun-1.4.4-fetch.json config/tls/bun-1.4.4-fetch.json

Then add this provider to config/config.hcl (replace the illustrative endpoint, model and secret source for real use):

provider "openai-compatible" "measured-bun" {
  base_url                  = "https://api.example.test/v1"
  api_key                   = env("UPSTREAM_API_KEY")
  tls_client_hello           = "custom"
  tls_client_hello_spec_file = "tls/bun-1.4.4-fetch.json"

  model "example-model" {}
}

The relative reference now resolves to config/tls/bun-1.4.4-fetch.json. Do not use a repository-relative examples/tls/... reference in an unrelated config directory. Only the recipe is loaded; metadata is documentation. For a complete checkout example, with synthetic credentials and no provider calls:

UPSTREAM_API_KEY=test-placeholder-key BACKUP_UPSTREAM_API_KEY=test-placeholder-key aiproxy validate --config examples/tls-client-hello.hcl

Mount custom recipes read-only alongside the config in containers, and ensure references resolve in that container's filesystem. Inline AIPROXY_CONFIG requires absolute references. Conversion output contains resolved absolute host-local paths; copy/mount recipes and adjust references when relocating to a different host. Replacing recipe files requires a successful reload to affect new work.

Provider TLS Transport Limits​

Native keeps Go's standard transport. For non-native HTTPS profiles, direct TLS and HTTP/1.1 CONNECT through HTTP or HTTPS environment proxies support HTTP/1.1/HTTP/2 according to ALPN. HTTPS proxy TLS is separately verified standard Go TLS with h1 CONNECT, not the provider profile; NO_PROXY remains effective. Non-native SOCKS5/ SOCKS5h, HTTP/2 CONNECT and QUIC/HTTP/3 are explicitly unsupported, with no native or protocol fallback. Actual HTTP upstream requests still use standard HTTP.

TCP dial/keepalive is 30 seconds, TLS handshake 10 seconds and CONNECT one minute, subject to earlier cancellation/deadlines. CONNECT response headers are bounded to 10 MiB, with at most eight cached TLS route entries including direct. Provider upstream_header_timeout remains header-only, with no added whole-inference or stream-read timeout. Health and discovery retain their separate operation deadlines and discovery pagination/aggregate limits. OAuth/device/dashboard clients and User-Agent behavior are unaffected. Fix unsupported proxy or upstream negotiation instead of disabling verification or cycling profiles.

Reload Behavior​

aiproxy supports live config reload on SIGHUP for runtime state such as:

  • auth configuration
  • provider and model inventory
  • static model-ID passthrough rules and their static client grants
  • root and provider upstream header timeouts
  • provider TLS ClientHello selections and custom recipe contents
  • alias routing state
  • root/provider/model/alias encrypted-reasoning policies
  • access-log enablement
  • payload-log configuration
  • metrics configuration
  • provider-health configuration
  • metrics-backed inventory state
  • static peer deferred transport / receiver policy, subject to live reservation checks and drain rules

If rate-limit settings are unchanged, reload preserves existing limiter buckets. Changing rate-limit settings creates a fresh limiter and resets bucket state.

TLS recipes and transport generations are prepared before activation. Successful reloads select new profile identities (including custom content changes at the same path) for new work and retire old idle connections. Already-admitted requests, their later alias attempts and streams finish against their admitted runtime; retired connections close as their bodies finish. Changed profile identities restart probe-owned clients, while discovery owns and retires a client per listing operation. A failed candidate leaves old clients, probes and cached recipe bytes intact, even if the source file was replaced. No custom-file reads occur on requests.

Alias cooldown deadlines survive reload only for fingerprint-unchanged targets (resolved base_url, credential, upstream model, protocol); removed or changed targets are dropped, and failed reloads leave state untouched.

Reasoning policies resolve from the admitted runtime snapshot. New admissions use the new policy after activation; admitted direct/alias requests, their recovery/ failover attempts and established streams retain the old snapshot. A failed candidate leaves the old runtime intact. Stripping is lossy, not decryption; recovery gates and attempt limits remain in force across reload.

When multi-tenancy is enabled, database-backed providers, aliases, and inbound keys merge into the serving catalog on the same reload path (and automatically after admin API mutations). An invalid old or externally corrupted row — for example a provider whose encrypted credential no longer decrypts under the current encryption key, or an alias pointing at a removed target — fails the reload with the old catalog retained, independently refreshing keys, and blocks server startup the same way an invalid config file does. Use aiproxy validate --check-db to identify the offending row without running the server, then repair its credential or references. Retarget/delete referencers before disabling/deleting a referenced provider; the next valid mutation or SIGHUP picks the catalog back up.

Database inbound keys with expires_at stop authenticating at that timestamp, using the server clock, even if no reload occurs. Model listing, billing usage, and new inference requests (including SSE) return the standard JSON 401 auth_failed error (invalid client token) at or after expiry, before upstream I/O. Requests and streams already authenticated may finish. Static HCL clients and database keys without expiry do not expire. Changing a key's expiry, rotating it, or disabling/deleting it uses independent key reconciliation below; the stored deadline in an active runtime requires no database access per request.

These changes still require a restart:

  • listener address changes
  • listener timeout changes
  • logging level changes
  • enabling the dashboard after startup

Provider and alias administrative POST/PUT requests commit their complete aggregate before requesting runtime activation, then read the response view. Provider model write failures roll back metadata too. A concurrent aggregate edit returns 409; read current state and retry. A dependency conflict returns 400 without saving or requesting activation. 500 could not save catalog edit means no activation was requested. 500 saved but activation failed means the complete edit is in the database while the old runtime remains active: inspect server logs, resolve the failure and reload. 500 saved but response view unavailable means the edit was saved and activation succeeded, but the response view failed; read current state before retrying, especially before repeating a create. These outcomes do not promise a distributed transaction between the database and running proxies.

Updating Model-ID Passthrough​

Edit the rule and grant declarations in static configuration. There are no CLI flags or managed API/web controls to author them. Unrelated in-place aiproxy configure edits to HCL preserve rule blocks (including OpenCode protocol) and grant expressions; edits that cannot preserve them safely are rejected without rewriting the config. aiproxy convert preserves declarations between HCL and JSON and resolves env() as usual.

Use aiproxy validate with the candidate config before sending SIGHUP. Update rule regexes, protocols, capabilities and grants in the same candidate. They activate together for new admissions on that replica. An invalid regex, protocol, path-based base_url or grant rejects the whole candidate and keeps the last active rules and grants. Already-admitted requests, including streams, keep their original protocol and runtime. Deploy and reload the file on each replica.

Grant narrow families. A broad regex can admit newly launched or more expensive IDs as soon as the upstream offers them, without a proxy reload or catalog update. Rule usage is grouped and unpriced locally, not free or cost-capped. Use trusted, appropriately scoped upstream credentials and upstream-side model and spend controls; restricting the model field or path ID cannot guarantee what the upstream runs or charges. Copilot rules use the configured sidecar credential and never refresh it; follow the existing login and reload procedure on revocation. Local Copilot fixtures do not establish live GitHub access or model availability.

Bounded Replica Convergence​

Replicas sharing PostgreSQL reconcile durable catalog and key revisions every two seconds, without relying on notifications. Database triggers advance revisions in the mutation transaction for providers, models, aliases, targets, inbound keys, key grants and owner quota policies, including account/key and workspace deletion cascades. Reads certify a snapshot only when before/after revisions match; publication rechecks the catalog revision. Continuous edits can postpone application. Startup requires a valid current catalog; it does not start from a persisted cache.

30 seconds is the maximum stale-serving admission window, not a polling interval. Freshness starts at the beginning of the confirmed read, never at poll completion. Failed reads, mixed snapshots and failed candidate activation do not renew catalog freshness. Keys refresh independently: an invalid provider edit cannot prevent revocation. Key policy changes invalidate the local owner quota cache. This is not atomic cross-replica spending reservation or a funded workspace cap.

After freshness expires, new DB-key auth/listing/billing and applicable peer controls/replay return 503 serving_stale; managed direct/alias inference also fails before upstream I/O, including requests authenticated with static keys. Trusted HCL inference using HCL clients remains available; their model list omits stale managed models. Already-admitted requests, alias attempts, streams and draining jobs retain their resources and may finish. Peer jobs are still process-local and have no replica failover. Fresh confirmed state restores admission automatically.

/healthz remains liveness. /readyz returns 503 when either database freshness deadline expires, even if HCL traffic remains available. Authenticated system administrators can read GET /_internal/admin/serving-status for applied revisions, confirmation timestamps and current freshness. These are local observations; cluster_acknowledged is always false. Catalog mutation responses expose X-Aiproxy-Local-Active, X-Aiproxy-Cluster-Acknowledged and applied catalog/key revision headers separately from durable-save headers. A failed catalog activation can still have successfully applied key revocation. No response proves every replica has acknowledged an edit.

Management/session operations still use their existing live database reads and authorization checks; serving freshness is not a management or browser-session cache. Database failures deny authorization or fail the operation under the existing route error contract, not a universal new outage status. The status endpoint itself requires successful live administrator authorization. File changes, credentials in sidecars and operator origin approvals still require consistent deployment/reload on every replica; durable revisions track DB mutations only. PostgreSQL must provide one coherent writable primary, with transactional triggers intact. This does not prove behavior under split brain, lagging read replicas, hostile trigger removal, process suspension or clock discontinuities. Verification uses two real apps with disposable PostgreSQL and mock upstreams, not a live cluster/provider certification.

Account Deletion And Local Revocation​

Permitted account deletion cascades to personally owned database keys and requests one local reload after commit. A successful response rejects those bearers on new requests to the receiving instance. Team-owned and other users' keys and durable spend history survive (the deleted user's ledger foreign key becomes null). Already-admitted requests/streams may finish. Workspace offboarding still only removes management memberships/shares; it does not revoke distributed tokens. Key updates, deletes, rotations and revocations for keys hidden after offboarding now return 404, not 403. This does not disable the key; an authorized manager must still rotate or revoke it to stop accepting a distributed bearer.

Confirmed deletion responses carry X-Aiproxy-User-Deleted: true, X-Aiproxy-User-ID and Cache-Control: no-store, including 500 saved but activation failed. In that failure case the database deletion is durable. Independent key refresh may already reject deleted bearers even if catalog activation failed; otherwise the stale-serving deadline bounds admission. Inspect server logs, repair the activation problem and reload with SIGHUP or restart the receiving server. Repeating DELETE returns 404 and does not retry activation. If the response was lost, reconcile account presence through the authorized user list rather than assuming rollback. Rejections preserve the account and request no reload. Responses acknowledge one instance; other replicas reconcile independently.

Database Key Issuance Recovery​

Key creation now saves the key, owner and all grants atomically. Binding or authorization rejection and key/grant write failures leave no partial issuance and request no reload. Successful commit requests activation once. A subsequent activation or response-view failure is explicitly saved, not rolled back: creation and rotation supply X-Aiproxy-Key-Saved: true, X-Aiproxy-Key-ID and a Location for the saved key, with the ID and recovery instruction in the error body as well. Responses containing issuance results use Cache-Control: no-store.

If a one-time bearer was not delivered:

  1. Do not create another key under a different name. Read the saved ID from the headers/body, or find the original globally unique name in the authorized key list if the response was lost. A connection failure can leave the database commit outcome unknown; missing saved headers do not prove nothing was saved.
  2. Inspect logs and resolve any activation failure. The saved key's intended owner/grants are complete, but the receiving instance may still use its old runtime. There is no cluster-wide activation acknowledgement.
  3. Rotate that existing key using its management action or POST /_internal/admin/keys/<key_id>/rotate. If you send workspace selectors, all must match the saved key's workspace. Securely distribute the returned bearer. Rotation keeps credential identity/workspace/grants and replaces the bearer after successful local activation. If rotation also saved without delivering a usable response, repeat rotation on the same ID.

The server never stores/replays plaintext inbound bearers; detail/list reads provide only a display prefix. A duplicate-name creation returns 409 without changing the saved key or requesting a reload. Offboarding can remove the original caller's management access after commit; an authorized workspace/global administrator must perform recovery in that case. See the issuance API contract.

Managed Catalog Dependencies And Cleanup​

Intentional compatibility change: managed provider deletion, disabling, model removal and inheritance/type/capability/protocol changes are rejected before durable commit if they invalidate a dependent alias or derivative. Aliases must still resolve every target in their destination workspace and share at least one supported capability. A disabled derivative still requires its enabled, concrete, same-type base and any inherited models named by local policy overlays. There is no cascade, automatic retargeting or force-delete option.

The API returns the generic 400 message catalog dependency conflict; retarget or remove dependent aliases and providers first. No dependency names, counts or credentials are returned. Rejection preserves provider/model/alias/target rows and revisions, leaves a Copilot device flow ready, and requests no reload. Concurrent graph writes serialize on the workspace's database lock, including alias/child creation, model replacement and Copilot aggregate saves; validation rereads the saved graph, not old managed runtime inventory. Current effective static System bases remain usable only in System, and tenant destination/credential restrictions still apply.

For planned cleanup:

  1. Retarget or delete aliases using the provider/model, including aliases targeting a derivative that inherits that model.
  2. Retarget or delete derivatives before removing/disabling their base or turning it into a derivative. Remove/retarget inherited model-policy overlays before removing their base model, even on disabled derivatives.
  3. Apply the provider/model edit, then run aiproxy validate --check-db and verify routing before restart. If a concurrent dependent write won, reread and repeat cleanup rather than blindly retrying the destructive edit.

Only affected dependencies are checked during a managed save, so unrelated corrupted rows do not prevent repairing known references or deleting an unreferenced corrupt provider. Full startup/reload/preflight still validates the whole catalog. A valid committed edit can therefore return 500 saved but activation failed for an unrelated corrupt row, credential/file failure or restart-only listener change. Repair that operational failure and reload; the valid edit remains saved. Provider DELETE, like provider/credential saves, carries X-Aiproxy-Catalog-Saved: true after commit, including activation failure. This is database graph integrity, not replica convergence or live upstream compatibility verification. Direct SQL and HCL edits must maintain references themselves and pass the candidate binary's preflight before restart; direct SQL must also follow the updated_at revision protocol.

Managed Reasoning Policy Storage And Activation​

Existing databases require aiproxy migrate up for the additive nullable provider/model policy columns. The migration does not rewrite/delete old model rows. Store only local intent: SQL NULL for absence, {} for reset and sparse objects for overrides. Stored JSON null is treated as absence; new writes use SQL NULL. Pre-feature derivative model rows with null policy remain inert legacy rows, not new model definitions or overlays.

Malformed stored policies, forbidden active overlays or a base-model removal that leaves an overlay dangling reject startup/reload; the old runtime survives a failed reload. This is not a silent corruption fallback. Correct the saved declaration/base inventory and reload. Credential-only edits preserve policies and cannot be used to change them.

The admin API exposes the full inherited model inventory, nullable local intent and normalized effective/source/inherited metadata. Omitted provider/alias policy preserves it, null removes it, and an object replaces it wholesale. In contrast, omitted or null models preserves the whole collection; arrays replace local definitions/overlays. Read-only inherited GET definitions must not be submitted as local derivative definitions. See the exact managed update contract.

Metadata describes saved intent, not successful activation. Durable provider/ credential saves carry X-Aiproxy-Catalog-Saved: true, including saved-but- activation-failed outcomes; old serving state remains active on failure. Immediate activation applies to the receiving instance; durable revisions reconcile other replicas independently, with no cluster-wide acknowledgement. Root remains static configuration and existing RBAC is unchanged. Managed provider/model/alias web forms offer inherit, safe reset and sparse custom policy controls; static rows expose read-only local intent and effective context.

Use reload for routing and auth changes, not for socket-level listener changes.

Spending Contract: Owner Quotas, Not Funded Workspace Caps​

This release does not support a funded workspace cap or a hard spending bound. Workspace ownership and usage reporting establish routing/reporting scope, not a funded pool, payer assignment or workspace budget authority. The proxy does not assign financial responsibility: payment remains outside proxy configuration under the operator's/provider's external agreement. User/team budget_micros settings are admission thresholds against recorded estimated spend, not prepaid balances or guarantees about upstream invoices. There is no workspace budget quota endpoint or workspace quota scope.

The DB schema permits at most one owner. Sharing grants management access, not a new charging scope or knowledge of who actually used a distributed bearer. Omitting owner_type when a workspace/global administrator issues a key creates an ownerless key; an ordinary member defaults to their own user ownership. Administrators may explicitly select a workspace-member user or local team; non-administrators may issue only personal keys for themselves or team keys for teams they administer. Labels and browser roles do not establish a payer.

Quota authority: A workspace administrator (or global system administrator) can set/reset member user and local team budgets and set TPM ceilings. An ordinary user can read their own quota and change its effective TPM within a positive administrator ceiling; a team administrator can do the same for their team. Ordinary team members may read, not edit, team quotas. Self/team administrators cannot set budgets, reset spend or set ceilings by virtue of those roles. A zero ceiling imposes no ceiling on an effective setting; effective zero falls back to the ceiling, rather than disabling a positive ceiling. These permissions concern owner quotas, not a workspace-wide budget.

Admission and overshoot: A missing or zero budget is unlimited. A positive budget rejects new admissions with 403 budget_exceeded when cached lifetime owner spend minus the reset offset (floored at zero) reaches the threshold. TPM checks the requested public model (including an alias name) against completed tokens in this process's trailing one-minute window, using positive effective TPM or else the ceiling. Exhaustion returns 429 tpm_exceeded. Neither check reserves tokens/money, predicts request cost, or atomically commits admission with a charge. Concurrent requests can all pass before any completes; a single long request or stream can overshoot by itself. Admission does not cancel admitted work or stop a stream at the threshold. Usage is recorded at completion, not as tokens stream. There is no promised maximum overshoot.

Accounting gaps: Ordinary inference persists available result usage only for downstream 2xx responses. A failed attempt, interrupted stream or upstream billable operation is not guaranteed to have complete reported result usage. No positive recognized usage means no ledger entry; durable request counts are therefore not all admissions. Tokens use positive total_tokens, otherwise prompt plus completion. Missing model pricing, unavailable cost calculation or total-only usage can record tokens with zero cost. Incomplete configured rates can underprice usage; cost is calculated from reported categories using the admitted catalog's pricing and truncated to integer micro-USD. Zero ledger cost does not establish free upstream service. No missing-data reservation or invoice reconciliation is implemented. Ledger-write failures are logged; ordinary requests are not undone and there is no durable retry queue. Peer deferred finalization reports sink failures separately, not a funded reservation system.

Lifetimes and replicas: Durable ledger amounts are stored at completion; price edits do not reprice those entries. Owner budgets use lifetime sums minus explicit reset offsets, not a calendar billing period. The separate GET /v1/billing/usage rolling estimate expires near 24 hours, can reprice with current prices and resets on restart; it is neither the quota ledger nor an invoice. Spend caches last 30 seconds per tracker and are not updated by each completion; a quota edit invalidates only the receiving tracker. Replicas share the DB ledger, not cached spend, TPM windows or atomic reservations. Restart loses TPM history; it does not erase durable spend. A fresh replica can read recorded exhaustion while another still admits against fresh cached headroom. Replica credential/catalog convergence is a separate deployment requirement; even convergence does not turn these thresholds into financial bounds.

Any future funded-cap feature is deferred, not current release readiness. It would first require an explicit payer/coverage/authority contract for every credential type; atomic cross-replica reservation before dispatch (including streams and retries); settlement and reconciliation rules; fail-closed rules for missing usage/prices and store outages; and recovery/idempotency rules for cancellation, deletion, lost completions, crashes and reservation expiry. No such financial policy or implementation is supplied by this release.

Deletion And Resets​

With multi-tenancy enabled, deleting an inbound key preserves its recorded spend and user/team owner attribution. Requests already admitted with that key still can record available usage when they finish, including streamed responses, provided the workspace and owner still exist and the ledger write succeeds. Creating a replacement key, even with the same name, does not restore the owner's budget; scope totals survive spend-cache refresh and server restart. Sharing a key does not transfer its spend to the other users or teams with access.

Deleting the owner account/team is different from deleting only a key. Existing ledger entries retain key/workspace/tokens/cost, but their deleted user/team reference becomes null and is no longer included in that owner's scope sum. Already-admitted work retains the old authentication snapshot; a new ledger insert referring to the deleted owner fails its foreign key. It is not automatically retried or reattributed to an ownerless scope. The rolling usage event can still be recorded under its admitted key/workspace identity. Account-deletion revocation does not cancel admitted work or guarantee a durable late charge. Workspace deletion cascades ledger and key identities and also prevents their late writes. Preserve external billing records if account/workspace deletion must not affect financial evidence.

A workspace administrator can explicitly reset a user/team budget's spend with reset_spend: true on its quota endpoint. Resetting records an offset against the current total; it does not delete historical usage. A request whose usage is recorded after the reset counts against the new budget, even if it started before the reset or its key has been deleted. Budget checks retain their existing 30-second cache and completion-based accounting; already-admitted requests may exceed the budget.

Quota policy reads distinguish missing rows (unlimited) from storage errors. When required budget/TPM rows cannot be read, or spend cannot be read for a positive budget with a cold or expired cache, new inference requests return JSON 503 quota_unavailable before any upstream call. This also applies to SSE requests, which receive JSON rather than a started stream. Storage causes are logged server-side; the response contains no database details. Retry after storage recovers. Actual budget exhaustion remains 403 budget_exceeded, and actual TPM exhaustion remains 429 tpm_exceeded with Retry-After.

A fresh spend-cache entry remains usable within its existing 30-second TTL, including for budget denial. Failed refreshes neither cache zero nor extend an expired entry. Policy rows are still read on each request, even with fresh cached spend. A genuinely missing or zero budget needs no spend read for admission; static HCL credentials do not acquire database quota dependencies. Admin quota views read current spend even without a budget and fail with a controlled 500 if the data is unavailable. Admin edits stop on failed policy reads; if an edit saves successfully but its response view cannot be read, the error explicitly says the quota was saved. Inspect the view after recovery before repeating that edit.

The forward database migration retains key and workspace UUIDs for accounting, without retaining deleted credentials. These identities and the ledger remain until the workspace is deleted. Previously erased spend cannot be recovered by the migration.

Peer Deferred Transport v1​

Use the two-role configurations and versioned wire contract. The only replaced leg is:

end client → caller proxy → finite peer controls → executor proxy → upstream

The end-client and executor–upstream connections still have their own deadlines and intermediary idle limits. This is not durable job scheduling, Batch, or Responses background mode.

Caller transport is selected per resolved model, including each alias attempt. Use model-level deferred_transport to keep ordinary and deferred chat models under one provider/credential. An explicit local provider block remains a compatibility default; a model block replaces it wholesale using standard defaults for omitted fields. There is no model opt-out from a provider default: remove that default when migrating to mixed models. Receiver eligibility stays provider-only and additive; it does not turn ordinary requests for its models into jobs. See the mixed-model pair and migration rules.

Streaming And Deployment​

The executor keeps the original stream flag. Reads are immediate, finite byte snapshots, not long polls. JSON delivery waits for the complete terminal manifest; SSE delivery starts when the selected adapter head is available and retrieves output incrementally. The retained bytes are exactly the existing adapter's output, including native SSE where passthrough applies. No synthetic SSE IDs, events, heartbeats or [DONE] are added.

Polling adds latency (normally at least the empty-poll interval). A silent upstream remains silent to the end client. Incomplete peer transfers are discarded and retried at the same byte cursor only after a complete frame can be validated. The terminal SHA-256 verifies all retained bytes, but cannot undo bytes already delivered to a streaming client. A failure after downstream headers/bytes are committed terminates that stream; it never splices in another inference. Peer cursor recovery is not an end-client reconnect/resume session.

Deploy compatible executors before enabling caller opt-ins. A positive, version-1 capability for the configured executor public model is required before submission. Missing capabilities or wrong versions mean zero submissions; opted-in chat never silently falls back to ordinary transport. An ordinary upstream 202 is not a job acknowledgment. Models without an effective caller opt-in continue to call ordinary routes, even if that executor/model also accepts private jobs. Responses and embeddings remain ordinary even on opted-in caller models.

Route capability discovery, submit/replay, reads, status, result and DELETE to the same executing process, using sticky routing or a dedicated executor. Expose the versioned private routes through the trusted TLS edge without caching or redirects; preserve their authentication and protocol markers. An external path mount must be stripped before the executor listener. Shared databases or Redis provider health do not share job storage.

All job data, generations, tickets and dedup evidence are in memory. Restart, replica replacement or rolling deployment loses them, even if external inference or billing continues. v1 provides no replica failover, restart recovery, exactly-once external inference or billing-stop guarantee. Drain the old process rather than moving its controls to a replacement.

Every control, including DELETE and accepted submit replay, authenticates against the current activated inference auth policy and checks the current allowlist for the admitted public name. Capabilities and new submissions check workspace ownership of the current model and the entire alias pool. Accepted replays and controls must match the job's admitted owner and workspace; they do not re-resolve, reselect, or require a current catalog entry for that job's target. Revocation denies further access but does not undo already-started work. A peer credential for a hosted HCL receiver's System models must be scoped to System.

  • A static owner is the named client plus tenant. Token rotation preserves ownership but rejects the old token; reusing a client name/tenant reuses identity.
  • A database inbound key owns work by its key ID and workspace ID, including the all-zero ID for System. Rotation preserves ownership; a replacement key is a different owner.
  • Anonymous requests and dashboard/admin JWTs cannot access peer controls.
  • Unknown/different-owner jobs return 404 job_unavailable. Current model denial returns 403, without revealing a result or permitting deletion.

A shared peer credential identifies the caller proxy, not end users behind it. Their jobs share that owner's limits and authorization at the executor; caller-side user/tenant headers cannot establish executor ownership. Keep the peer credential separate from end-client and upstream credentials.

Controls forward no end-client credentials, cookies or arbitrary inference headers. The submit header bag is bounded ordinary adapter metadata (JSON content type, Accept, chosen inference user-agent and configured safe forwarded headers). The executor uses its own upstream credentials and normal adapter policies. forward_authorization is incompatible with either opt-in. The case-insensitive X-Aiproxy-Deferred / X-Aiproxy-Deferred-* namespace is reserved, rejected in generic forwarding configuration and stripped from inference header bags. TLS/proxy behavior remains configured per provider; private controls forbid all redirects, even same-origin redirects. Health/discovery never submit jobs.

Once a receipt is known, the caller makes one best-effort DELETE on cancellation or delivery completion. It has an independent fresh control deadline and does not use the canceled request context or retrieval budgets. A lost receipt may leave no job ID to delete. DELETE promptly seals/revokes appends and releases retained data; a known repeated release returns 204. It cannot prove the external provider stopped work or charging. Execution deadlines and terminal TTL remain cleanup backstops even if DELETE fails or current authorization prevents it.

Deletion/expiry retains protected dedup tombstones, not result bodies. A caller that has begun submit freezes its generation, signed ticket, attempt key and prepared request. Lost acknowledgments can retry only that same qualified submit. Never recover an accepted or indeterminate control failure by refreshing the ticket/key, starting ordinary inference or choosing another alias target.

Resource Bounds​

Admission reserves job/running/owner/dedup capacity, the full output allowance, input and work memory, and finalization credit before 202. There is no inference queue. Saturation can occur below max_running or max_jobs because memory, per-owner capacity, control slots and outstanding finalization ownership also constrain admission. Accepted records/tombstones are not evicted early to make room.

max_memory_bytes accounts feature-owned live capacity/reservations, including decoded/base64 submit scratch, request rewrites/redaction, parser/translation work, output slabs, control frames/readers and completion snapshots. It is not a total Go heap/RSS or ordinary-connection limit. Output uses 32 KiB slabs; each finite read copies at most 64 KiB rather than retaining a deleted full buffer. Fixed allowances include 512 KiB/control slot, 64 KiB/job metadata, 4 KiB/dedup record and 1 KiB/owner bucket.

Deferred-only structural bounds are JSON depth 64 / 16384 tokens; SSE line 256 KiB / event 1 MiB / 1024 data lines; and control JSON depth 8 / 2048 tokens. Required translated parsing fails explicitly on overflow. Optional passthrough usage inspection can stop inspecting an oversized event without changing its delivered bytes. Buffered upstream bodies still obey the effective result ceiling.

Payload capture is absent when logging is off and otherwise limited by both the configured capture prefix and effective request/result ceilings. payload_log.max_body_bytes = 0 does not make deferred snapshots unbounded. On growth/structural/capture-work failure, the job fails explicitly, cancels/closes its source and finalizes once. It may retain an exact failed stream prefix, never a truncated success. Ordinary non-deferred adapter limits are unchanged.

Non-delete controls have fixed global 100/s (burst 200) and per-owner 20/s (burst 40) buckets, at most four in flight per owner and one active control per job. DELETE has two reserved global slots, global 8/s (burst 16) and per-owner 2/s (burst 4) buckets. Owner tables are bounded by max_entries; idle, job-free owners can be reclaimed after one minute, not evicted to reset live limits.

Peer Reload And Finalization​

Accepted execution retains its admitted catalog, credentials, endpoint, transports, alias attempts and completion resources through a runtime lease. Per-job deadlines/limits stay frozen; current auth/model policy still governs controls. Failed reloads leave jobs and resources intact.

Caller model policy also reloads on SIGHUP. New requests use the activated model opt-ins, provider compatibility defaults, endpoint and credentials. Already admitted jobs and committed streams keep their original peer, credential, caller options and runtime resources through delivery/cleanup. Moving or removing a caller model block changes new requests only; it never converts an admitted attempt into synchronous inference or a fresh alias attempt.

To disable new execution, remove the root deferred block and all receiver blocks in a valid reload. Capabilities/new admissions then stop, while existing authenticated status/read/result/DELETE and protected submit replay drain under the last resource/control policy, even if opt-ins disappeared. Re-enablement and capacity reductions are checked against live ownership. Reducing global/owner job, running, admission, entry, control or memory capacity below reservations rejects activation; jobs are not evicted to fit.

Two fixed app-owned completion workers handle at most max_jobs outstanding records, with credit reserved at admission. Known in-memory completion/usage is published once. Remote health/quota/payload completion has a deadline from terminal sealing plus finalization_timeout, including queue wait. Failed or expired persistence is reported, not retried into duplicate accounting.

Local filesystem payload I/O has no hard cancellation guarantee: operation assumes local OS/filesystem calls complete in bounded time. A blocked call can occupy one of the two workers and its resource lease, applying admission backpressure; no unbounded timeout goroutines or replacement workers are spawned. Shutdown first stops admission and cancels sources, then waits within the app's shutdown budget (default 10s), reporting incomplete cleanup rather than falsely freeing live ownership. Runtime resources retire only after their last lease.

Metrics And Health​

The proxy exposes Prometheus metrics at GET /metrics.

Coverage includes:

  • inbound request counts and latency
  • streaming counts and duration
  • provider selection counts
  • alias retry counts
  • alias in-flight gauges
  • provider health state
  • readiness state and reason
  • upstream request counts, latency, and response sizes
  • provider health backend error counts
  • provider health fallback counts by operation and reason

/metrics requires a dedicated bearer token declared in a metrics block:

metrics {
  token = env("AIPROXY_METRICS_TOKEN")
}

GET /metrics without a valid Authorization: Bearer <metrics token> header returns 401. The metrics token is checked independently of API auth client tokens; API clients cannot scrape /metrics with their own credentials. An empty or missing token is rejected at config validation.

Transient transport failures, upstream request errors, and upstream 5xx responses can mark a provider unhealthy for routing and readiness decisions. Configured retryable 4xx statuses can trigger alias failover but do not mark providers unhealthy.

Alias upstream retry advice (retry-after-ms, else Retry-After) is tracked separately from provider health as process-local per-target cooldown deadlines. It is never shared across processes or via Redis, never marks providers unhealthy, and leaves skipped targets out of upstream attribution while the client-facing 429 stays visible in HTTP accounting and metrics.

This health state is shared across requests within the same process.

Shared Provider Health​

Without extra config, provider health is in-process only.

You can optionally configure Redis-backed shared health state with provider_health so multiple instances can observe the same transient provider status.

provider_health {
  redis_url  = env("AIPROXY_REDIS_URL")
  key_prefix = "aiproxy:provider-health"
  cooldown   = "30s"
  cache_ttl  = "30s"
}

cache_ttl (default 30s) bounds how long a stale in-process cache entry is reused for routing and readiness when the Redis backend becomes unreadable. When a Redis health read fails, routing, readiness, and dashboard snapshots fall back to the bounded in-process cache and fail open only when no fresh cache entry exists; both the backend error and the fallback reason are recorded as Prometheus metrics so degraded mode is observable.

Without Redis-backed sharing, each instance tracks transient health independently.

Dashboard Transport Security​

The aiproxy dashboard command and the /_internal/dashboard/* HTTP endpoints share the proxy listener.

  • Listener addresses are TCP bind addresses in host:port form, not URLs.
  • The dashboard command is local-only. It connects over loopback plain HTTP with bearer authentication and refuses concrete non-loopback listener hosts.
  • HTTPS and remote dashboard URLs are not supported by the current configuration model. Remote dashboard access requires a future explicit transport design.
  • Repeated invalid dashboard tokens are rate limited with 429 and a Retry-After header.

The embedded web dashboard is served at / when a web_ui block is present. Use aiproxy webui to print that URL after probing that a running server answers with the UI (--open also launches the default browser). The UI's live views call the same dashboard-gated /_internal/dashboard/* APIs as the TUI. With multi-tenancy enabled, the Web UI uses the signed-in system administrator's session and never falls back to a saved dashboard token. With multi-tenancy disabled, the Web UI uses the token entered on its Token page. The TUI uses its dashboard token in either mode. Ordinary accounts and workspace administrators cannot access these global operator surfaces with their account sessions.

Within a loaded browser tab, changing accounts, changing/removing the dashboard token, or selecting another workspace clears sensitive cached data and open detail/dialog state. Delayed responses from the previous context are discarded. Account replacement also resets the selected workspace. A successful normal token refresh preserves the current account's cache and workspace; a failed refresh clears the account session. Sign out clears the local account, workspace selection, and dashboard token immediately, even if server-side session revocation is delayed or fails. Dashboard tokens are installed only after successful validation. These transitions are local to the current tab; other already-open tabs do not automatically synchronize their in-memory sessions.

Security Defaults​

  • API keys and client bearer tokens are never logged
  • prompt and response bodies should be redacted or omitted from standard logs
  • request IDs are emitted for correlation

Logging​

Use the optional logging block to control structured log verbosity and request lifecycle access logging.

logging {
  level      = "info"
  access_log = true
}

When access_log = true, request logs include events for request receipt, upstream provider/model selection and completion, and the final response or streaming start and end.

Payload logging​

The optional nested payload_log block records request/response headers and bodies as JSONL (one JSON object per line per inference request). It is disabled by default. Each entry carries three sides: request (inbound headers and body as received), upstream_request (headers and body actually sent upstream, after model rewrites and provider translation; present only when an upstream call was made, so alias retries log the final attempt), and response (the upstream reply, or the proxy's own error on early rejections). Credential headers (Authorization, x-api-key, x-goog-api-key, cookies) are redacted on every side, and bodies covered by an ingress-guardrail policy (chat completions, responses, messages) are omitted from the request and upstream request sides unless redact_guardrail_bodies is enabled.

logging {
  level      = "info"
  access_log = true

  payload_log {
    enabled        = true
    dir            = "/var/log/aiproxy/payloads"
    rotation       = "daily"
    retention      = "168h"
    max_body_bytes = 1048576

    mongodb {
      uri        = env("AIPROXY_PAYLOAD_MONGO_URI")
      database   = "aiproxy"
      collection = "payloads"
      timeout    = "5s"
    }
  }
}

With redact_guardrail_bodies = true and an ingress guardrail policy enabled, guardrail-covered request bodies are logged with gitleaks-flagged text replaced by the guardrail redact_placeholder instead of being omitted. The split is decision-aware: the request side masks every flagged occurrence (determined by the scan, independent of quarantine decisions), while the upstream_request side shows the body that was actually sent upstream — so after an operator allows a finding as non-secret and the client resends, the literal text appears on the upstream side; redact decisions appear as the placeholder; requests still blocked or denied never reach upstream, so those entries carry no upstream side. Audit-mode requests proceed upstream, so their upstream side contains flagged text verbatim. Bodies that were never scanned (early rejections before the guardrail scan) or scans that could not complete (unparsable or multipart bodies, oversize text, captures cut off by the findings cap) stay omitted on both sides. Redaction operates on decoded JSON, including JSON-encoded tool arguments, and safely escapes the replacement while preserving JSON numbers. Bodies that exceed the 128-level rewrite nesting bound (including embedded JSON) or cannot be completely rewritten stay omitted on both sides. Because masking depends on the scanner's coverage and rules, opting in accepts that unscanned or unrecognized secrets could reach the log; keep the output directory protected either way.

The logging setting never selects guardrail admission behavior. Fingerprint exceptions apply with or without quarantine/logging, but an incomplete capture cannot clear block-mode findings through exceptions. Exactly-at-cap captures remain complete when no findings were dropped. A block-mode redact decision that cannot be rewritten safely returns 400 scan_incomplete; audit mode instead forwards the original body and omits both logged request sides. Standard response capture remains unchanged; response scanning/redaction is not provided by this setting.

The disk backend (dir) and the MongoDB backend (mongodb) are enabled independently: set dir for JSONL files, uri for one MongoDB document per request with the same JSON field names, or both to fan out to both. When enabled, at least one backend is required. Recording is best-effort and never fails a request; a bad MongoDB URI fails startup fast instead.

The dashboard and TUI payload viewer read from the disk backend only: with MongoDB-only logging (no dir), the viewer reports payload logging as disabled.

Files are split by datetime so no single file grows without bound: daily rotation writes payload-YYYYMMDD.jsonl and hourly writes payload-YYYYMMDD-HH.jsonl (UTC) under dir (0600 files, 0700 directory). retention (default 7 days, "168h") controls how long files are kept: files older than the retention window are removed on rotation and by an hourly sweep; "0s" disables expiry. Bodies larger than max_body_bytes per side are truncated with "truncated": true (0 stores full bodies), and sensitive headers (authorization, proxy-authorization, cookie, set-cookie, x-api-key) are stored as [REDACTED].

Only enable payload logging when you can protect the output directory: bodies contain prompts and completions. Changes apply on SIGHUP reload.

Deferred inference additionally obeys its effective request/result and work ceilings; a configured full-body capture does not remove those bounds. Peer control envelopes/polls are not payload entries. See peer diagnostics and finalization.

Secret Handling​

When api_key_ref is used, the default key file path is:

  • $XDG_CONFIG_HOME/aiproxy/keys.json
  • or ~/.config/aiproxy/keys.json

Mount this file read-only in production deployments.

GitHub Copilot logins live beside that file as copilot-<name>.json sidecars (0600, restrictive parent directory). credential_ref.path defaults to the same secrets path; mount the secrets directory (not just keys.json) when Copilot providers are configured, and reload with SIGHUP or a restart after every login or sidecar rotation.

Production Checklist​

  • enable bearer_static auth unless the deployment is fully trusted
  • keep provider secrets out of the HCL file when possible
  • mount config and key files read-only
  • when using static custom TLS profiles, mount recipe files read-only at their config-relative paths and validate replacements before reload; do not rely on ClientHello matching as a provider/WAF-acceptance guarantee
  • declare metrics { token = env("AIPROXY_METRICS_TOKEN") } and scrape GET /metrics with the configured bearer token
  • use aiproxy dashboard only from the local host; remote dashboard access is unsupported until an explicit transport design is added
  • explicitly enabled = false any provider you want to keep defined but inactive; missing credentials on enabled providers fail validation
  • use aliases for controlled failover instead of relying on direct model requests
